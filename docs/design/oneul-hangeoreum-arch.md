## 0. 전제와 범위 경계

| 구분 | 내용 |
|---|---|
| 목표 | 기획서의 핵심 흐름이 **실제 데이터로 동작**하는 웹앱. 청년·회복 선배·상담사 3역할이 각자 로그인해 실제로 주고받는다. |
| 사용 대상 | **팀·심사용 데모 계정만.** 실제 고립·은둔 청년의 가입은 받지 않는다(아래 리스크 R1). |
| 시간 | 실작업 약 1.5일. 그래서 P0만 완성을 약속하고 P1·P2는 시간이 남으면 진행. |
| 언어 | TypeScript (Vercel·Next.js에 맞춤) |

### 기능 우선순위

| 우선 | 기능 | 기획서 근거 |
|---|---|---|
| **P0** | 3역할 로그인(시드된 데모 계정 + 초대 코드 가입) | 보조 사용자 구조 |
| **P0** | 선배와 메시지 주고받기(새로고침/폴링) → 양방향 접촉 자동 판정 → 단계 표시·제안·수락 | 핵심 기능 ① |
| **P0** | 위기 감지(규칙, 즉시) → 109 시트 + 상담사 대시보드 알림 + 미확인 재전달(시연 시 60초) | 5장 윤리 |
| **P0.5** | 아침 체크 + 오늘의 한 걸음(Claude 제안, 실패 시 기본 걸음) | 사용 시나리오 |
| P1 | AI 대화(짧게 듣고 선배 글로 잇기), 첫 문장 함께 쓰기, LLM 위험 분류(비동기 보조) | 핵심 기능 ① |
| P1 | 재연결 약속(동의 + 무활동 시 '돌아올 문') — 상담사 화면 "지금 실행" 버튼으로 시연 | 핵심 기능 ③ |
| P2 | 상시 대기실, 가족 코치, 오프라인 만남 확인, 이메일 알림, Realtime | 보조 |

**시연 가능성 원칙:** 시간에 의존하는 규칙(재전달 30분, 단계 2주, 재연결 14일)은 모두 DB 설정 테이블 `app_config`에서 간격을 바꿀 수 있게 하고, 14일치 과거 접촉 데이터를 시드로 넣으며, 상담사 화면에 "단계 재계산"·"재연결 실행" 버튼을 둔다. 심사위원이 몇 분 안에 전체 흐름을 볼 수 있어야 한다.

**데모 상태 관리:** 시드 스크립트는 여러 번 실행해도 같은 결과가 나오게(idempotent) 만든다. 상담사 화면에 **"데모 초기화"** 버튼을 두어 시드 계정의 이벤트를 지우고 다시 넣는다. 초기화는 **누른 사람이 속한 데모 세트만** 대상으로 한다. 청년 데모 계정은 3세트(청년·선배 짝)를 만들어 심사위원 여러 명이 동시에 써도 서로 상태를 오염시키지 않게 한다.

## 결정 1. 앱 프레임워크

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. Next.js (App Router) + TypeScript** | Vercel 1급 지원, 서버 라우트에서 API 키 보관, Server Actions로 폼 처리 간단 | App Router 캐싱 규칙이 까다로움 |
| B. Vite React SPA + 별도 API(Express/FastAPI) | 구조 단순 | 서버 배포가 따로 필요, 이틀 안에 두 군데 배포는 부담 |
| C. SvelteKit | 코드량 적음 | Codex·팀 익숙도 낮음, Vercel 예제 적음 |

**추천: A.** 배포 대상이 Vercel이고, LLM 키를 서버에만 둬야 하므로 한 저장소·한 배포로 끝나는 Next.js가 가장 빠르다.
**리스크:** 서버/클라이언트 컴포넌트 경계 실수 → 인증 관련 코드는 전부 서버 쪽에서만 처리하는 규칙으로 막는다.

## 결정 2. 데이터베이스·인증·실시간

> 2026-10-04 변경: 사용자의 Supabase 무료 플랜 한도 때문에 **Neon Postgres**로 바꿨다. 로그인은 자체 구현(scrypt 비밀번호 해시 + HMAC 서명 세션 쿠키), 권한 확인은 RLS 대신 서버 코드(`src/lib/auth.ts`의 `requireRole`·`canUseThread`, 각 쿼리의 담당 관계 조건)에서 한다. 위기 재전달은 pg_cron 없이 돌봄 대시보드 폴링 시 `escalate_alerts()`를 호출한다. 스키마는 `service/db/schema.sql`.

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. Supabase (Postgres + Auth + Realtime + RLS + pg_cron)** | 인증·DB·실시간 메시지·예약 작업이 한 곳. RLS로 "선배는 담당 청년의 메시지만" 같은 권한을 DB에서 강제 | Supabase 프로젝트·키 필요, RLS 정책 작성 시간 |
| B. Neon Postgres + Auth.js + Pusher | 각 부품 교체 쉬움 | 서비스 3개 연결, 이틀 안에는 과함 |
| C. Firebase | 실시간 쉬움 | 관계형 질의(단계 계산·통계)가 불편, 권한 규칙 표현력 낮음 |

**추천: A.** 민감정보(정신건강 기록)를 다루므로 권한을 앱 코드가 아니라 **DB 행 수준(RLS)** 에서 강제한다.

**설정 규칙 (평가 반영):**
- RLS 정책이 `profiles`·`assignments`를 서로 참조하면 무한 재귀가 나므로, 역할·담당 관계 확인은 `security definer` 함수 2개(`my_role()`, `is_assigned(youth_id)`)로만 한다.
- 이메일 확인은 끈다(무료 플랜 발송 한도). 데모 계정은 시드 스크립트로 미리 만들고, 로그인 화면에 데모 계정 안내를 둔다. Auth의 Site URL·Redirect URL에 Vercel 도메인을 등록한다.
- 무료 프로젝트는 7일 무활동 시 일시정지되므로, Vercel Cron(일 1회)으로 DB에 keepalive 질의를 보낸다.
- Realtime은 P2. P0는 메시지 화면 10초 폴링.

**리스크:** RLS 누락 시 다른 사용자 데이터 노출 → 모든 테이블 RLS 기본 거부 + 역할별 허용 정책, 배포 전 역할별(청년 A/청년 B/선배/상담사) 접근 테스트 필수.

## 결정 3. 데이터 모델

| 옵션 | 내용 | 판단 |
|---|---|---|
| **A. 이벤트 원장 + 파생 계산** | 메시지·모임·만남을 원본 이벤트로 저장하고, "양방향 접촉"과 단계는 그 위에서 계산 | 측정 기준이 바뀌어도 재계산 가능. Codex 리뷰에서 측정 정의가 여러 번 바뀐 점을 감안 |
| B. 카운터 컬럼 직접 증가 | `two_way_count += 1` | 빠르지만 정의가 바뀌면 과거 데이터 복구 불가 |

**추천: A.** 핵심 테이블:

```
profiles(id, role[youth|mentor|counselor], display_name, consent_sensitive, consent_reconnect, ...)
assignments(youth_id, mentor_id, counselor_id)            -- 선배 1명당 청년 10명 이내 제약
checkins(id, youth_id, date, mood[hard|ok|good])
daily_steps(id, youth_id, date, text, size[normal|small], done_at)
threads(id, youth_id, mentor_id)
messages(id, thread_id, sender_id, body, kind[text|voice|emoji], created_at)
reactions(id, youth_id, kind[read|emoji|attend_only|self_check], ref_id)   -- 참고 지표
contacts(id, youth_id, source[message_pair|meeting_talk|offline_confirmed], ref_id, occurred_at)  -- 양방향 접촉(파생)
stage_state(youth_id, stage 0..4, proposed_stage, proposed_at, accepted_at)
crisis_events(id, youth_id, source[rule|llm], severity[urgent|high], excerpt_hash, created_at)
alerts(id, crisis_event_id, recipient_id, level[primary|backup|emergency], sent_at, acked_at)
ai_turns(id, youth_id, role, content, created_at)          -- AI 대화 기록(본인만 열람)
programs(id, name, stage_min, recruit_start, recruit_end, url)   -- P2
reconnect_jobs(youth_id, due_at, kind[2w|1m], sent_at)    -- P1
```

**양방향 접촉 판정(기획서 기준 그대로):** 열람·이모지·단순 접속·본인 체크는 `reactions`로만 저장한다. `contacts`의 `message_pair` 규칙:
- 새 텍스트·음성 메시지가 들어왔을 때, **같은 스레드의 직전 메시지 발신자가 상대방**이고 그 시각이 72시간 이내면 1쌍.
- 같은 사람이 연속으로 보낸 메시지는 추가 쌍이 아니다.
- 이모지만 있는 메시지(`kind = emoji`)는 쌍을 만들지 않는다.

## 결정 4. 단계 엔진·시간 기반 작업

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 메시지 insert 트리거로 접촉 생성 + `pg_cron`으로 단계 제안·재전달·재연결** | DB 안에서 일관성, Vercel 크론 제한(무료 플랜은 하루 1회) 회피 | SQL 함수 작성 필요 |
| B. Vercel Cron + API 라우트 | TS로 작성 | 무료 플랜 크론 빈도 부족 → 30분 재전달 불가 |
| C. Upstash QStash 지연 메시지 | 정밀한 지연 실행 | 서비스 하나 추가 |

**추천: A를 단순화** (평가 반영: pg_cron만으로는 외부 알림을 못 보내고 pg_net이 따로 필요).
- 접촉 판정: 메시지 insert 트리거(SQL 함수)가 `contacts` 생성.
- 단계: `0~1 → 2`는 첫 `message_pair` 시 트리거에서 즉시 개방. 2단계부터의 제안(14일간 주별 접촉 ≥ 3회, 2주 연속)은 **요청 시 계산하는 SQL 함수**로 만들고, 청년 홈 진입 시와 상담사 "단계 재계산" 버튼에서 호출. 청년이 수락해야 반영.
- 위기 재전달: 외부 발송 없이 **`alerts` 행 상태만 변경**. 간격은 Vercel 환경변수가 아니라 **DB 설정 테이블 `app_config.escalation_seconds`**(기본 1800, 시연 60)에 둔다. `pg_cron` 1분 주기 함수와 대체 경로(대시보드 폴링 시 서버 호출) 모두 같은 값을 읽어, 경과한 미확인 알림을 다음 레벨(예비 담당 → 긴급) 행으로 추가한다. 1분 주기이므로 시연 대본에는 재전달까지 "약 1~2분"으로 적는다.
- 시간 관련 데모 값(`단계 기간`, `재연결 기간`)도 같은 `app_config` 테이블에 둔다.
- 재연결: 상담사 화면 "재연결 실행" 버튼(시드된 무활동 청년 대상) + 일 1회 Vercel Cron.

**리스크:** 무료 플랜에서 pg_cron이 막혀 있으면 → 상담사 대시보드 폴링 시 서버에서 같은 재전달 함수를 호출하는 방식으로 대체(시연 동작은 동일).

## 결정 5. LLM 연결 방식 (Gemini로 변경됨)

> 2026-10-04 변경: 사용자 요청으로 Google Gemini(`@google/genai`)를 사용한다. 모델은 환경변수 `GEMINI_MODEL`(기본 `gemini-flash-latest`), 구조화 출력은 `responseMimeType: application/json` + `responseJsonSchema`. 아래 원칙(서버에서만 호출, 실패 시 고정 문구, 위기 감지는 규칙 우선)은 그대로다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 서버 라우트에서 Anthropic TypeScript SDK 직접 호출, 용도별 짧은 단일 호출** | 단순, 키는 서버에만, 용도별 프롬프트·출력 형식 고정 | 대화 기억은 우리가 `ai_turns`로 관리 |
| B. 에이전트(도구 루프) | 확장성 | 이 서비스의 AI 역할은 단발 생성 위주라 과함 |

**추천: A.** 모델은 `claude-opus-5-5`(기본값), 응답 속도를 위해 전 용도 `effort: "low"`, 출력은 구조화 출력(`output_config.format`). 거절 대비 `fallbacks`는 구현 시 SDK 문서로 파라미터를 확인한 뒤에만 넣고, 확인되지 않으면 넣지 않는다. 모든 LLM 호출은 실패 시 고정 문구로 대체해 서비스가 멈추지 않게 한다.

| 용도 | 입력 | 출력 |
|---|---|---|
| 오늘의 한 걸음 | 컨디션, 최근 3일 걸음·완료 여부, 현재 단계 | 걸음 1개(작게/보통) JSON |
| 더 작게 쪼개기 | 기존 걸음 | 더 작은 걸음 1개 |
| AI 대화 | 최근 대화 몇 턴 | 짧은 응답 + (조건 충족 시) 선배 글 연결 제안 |
| 첫 문장 함께 쓰기 | 선배 글 | 답장 첫 문장 후보 3개 |
| 위험 분류 | 청년이 쓴 문장 | `{severity: none|high|urgent, reason}` |

**위기 감지 이중화:** ① 키워드·패턴 규칙이 메시지 저장 시점에 **동기로** 판정해 109 시트를 즉시 띄우고 알림을 만든다(LLM 장애와 무관). ② LLM 분류는 저장 후 **비동기**로 돌려 규칙이 놓친 표현을 보완한다(P1). 상담사 알림에는 해당 문장과 짧은 맥락을 본인 동의 예외 원칙(가입 시 고지)에 따라 보여 준다. 데모 데이터는 모두 가상 문장이다.
**리스크:** API 키·비용 → 사용자당 일일 호출 상한, 실패 시 고정 문구로 대체(서비스는 멈추지 않음).

## 결정 6. 알림 채널(위기 인계)

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 앱 내 상담사 대시보드 + 이메일(Resend)** | 이틀 안에 구현 가능, 확인(ack) 버튼으로 수신 확인 추적 | 이메일은 실시간성 약함 |
| B. 문자(SMS) 발송 | 실시간성 | 발신번호 사전등록·비용, 이틀 안 불가 |
| C. 카카오 알림톡 | 국내 사용성 최고 | 비즈채널·템플릿 심사로 불가 |

**추천: A의 앱 내 대시보드만 P0** (이메일은 P2). 기획서의 "24시간 위기대응팀 긴급 전화"는 MVP에서 **데모 '위기대응팀' 계정에 긴급 레벨 알림**으로 처리하고, 해당 화면에 **"시뮬레이션"** 라벨을 붙인다.
**리스크:** 데모가 실제 위기 대응처럼 보일 위험 → 모든 위기 화면에 "시연용 서비스입니다. 실제 위기라면 지금 109로 전화하세요" 고정 문구(R1).

## 결정 7. 디자인 분업(Codex)

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. Codex = 디자인 시스템 + 화면 컴포넌트(정적 props), Claude = 데이터·로직 연결** | 경계가 명확(컴포넌트 props 계약), 병렬 진행 가능 | props 계약을 먼저 정해야 함 |
| B. Codex가 화면 전체를 데이터 포함해 구현 | 한 번에 끝 | 인증·RLS·LLM 로직까지 넘어가 품질 통제 어려움 |
| C. 목업 HTML을 Claude가 그대로 이식 | 빠름 | 사용자가 디자인을 Codex에 맡기길 원함 |

**추천: A.** 순서: ① Claude가 프로젝트 골격 + 컴포넌트 props 타입(`ui/contracts.ts`) 작성 → ② Codex에 목업·기획서·contracts를 주고 `ui/` 아래 디자인 토큰(Tailwind)·화면 컴포넌트 제작 요청 → ③ Claude가 페이지에서 데이터 연결.
**리스크:** Codex 결과물이 계약을 어기면 통합 지연 → 정적 데모 페이지(`/design-preview`)에서 Codex 산출물을 먼저 검수한다. **전환 기준: 10/5 12:00까지 Codex UI가 계약대로 오지 않으면, 이미 있는 목업 HTML의 스타일을 Claude가 직접 옮긴다.** 로직 작업은 처음부터 Codex와 무관하게 진행하므로 전환해도 일정이 밀리지 않는다.

## 추가 설계 (10/5): 상시 대기실 · 재연결 약속

기획서 핵심 구성 ②·③을 시연 가능한 최소 형태로 만든다. 스키마 재실행 없이 `ensureMigrations()`가 테이블을 만든다(같은 내용을 `db/schema.sql`에도 둔다).

| 결정 | 선택 | 이유 |
|---|---|---|
| 프로그램 데이터 | `programs` 테이블에 **시연용 예시 공고 6건**(단계 2~4), 모집 마감·시작일은 배포 시점 기준 상대 날짜로 갱신 | 실제 공고 크롤링은 범위 밖. 실제 기관명·일정을 지어내지 않도록 "예시" 표기 |
| "단계에 맞는" 기준 | `min_stage ≤ 현재 단계 + 1` 이면 지원 가능, 나머지는 "N단계부터"로 흐리게 | 4단계가 도착지라 한 단계 앞 프로그램을 미리 보여 주는 것이 동기 |
| 지원서 초안 | Gemini가 **완료한 걸음 기록·접촉 횟수만** 근거로 300자 내외 초안 작성. 대화 내용·위기 기록은 넣지 않음. 실패 시 템플릿 | 민감정보 최소화. 기획서 "제출은 본인 승인" |
| 제출 | 청년이 초안을 고쳐 "이 내용으로 보내기"를 눌러야 `sent`. 보낸 지원서는 담당 상담사 화면에 보이고, 상담사가 기관에 전하는 구조(시연에서는 실제 전달 없음) | 본인 승인 + 기관 연계는 사람이 |
| 재연결 약속 | 청년이 2주/한 달 중 고르거나 안 함. 언제든 거둘 수 있음. `reconnect_promises` 1행 | 기획서 "본인이 동의한 범위·기간에만" |
| 끊김 판단 | 마지막 활동 = max(체크인, 청년이 보낸 글, 걸음 완료, 약속한 시각). 약속 기간을 넘기면 열림 | 별도 이벤트 수집 없이 기존 데이터로 계산 |
| 돌아올 문 전달 | 푸시가 없으므로 ① 선배·상담사 목록에 "약속한 재연결 · N일째 소식 없음" 표시(사람이 먼저 연락) ② 청년이 돌아오면 홈 맨 위에 **돌아올 문**(담당자에게 글 남기기, 다음 모집 일정, 다시 시작할 단계 선택) | 기획서의 세 요소(담당자 연락처·다음 모집·다시 시작할 단계)를 그대로 |
| 시연 | 상담사 시연 도구에 "3주 소식 없음(2주 약속)" 추가 | 날짜를 기다리지 않고 바로 보여 주기 |

리스크: 예시 공고가 실제 공고로 오해될 수 있음 → 대기실 상단과 지원서 화면에 "시연용 예시 공고, 실제 기관에 전달되지 않음" 고정.
